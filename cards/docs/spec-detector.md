# Спецификация детектора карт (`cardscan`)

Документ фиксирует принятые решения по распознаванию карт MTG на фото и видео.
Движок — нативный C++17 + OpenCV 4 + Tesseract 5, лежит в `cards/`.

## Задача

* Вход: фото (jpg/png/...) или видео (mp4/mov/...).
* Выход: список карт с кодом сета и номером коллекционера из нижнего левого угла,
  уверенность, координаты четырёхугольника карты, таймкоды показа (для видео).
* Для видео — количество показанных карт без ложных дублей.
* Отладочный оверлей: размеченное изображение/видео с найденными картами и результатом OCR.

## Конвейер

```
кадр → кард-кандидаты (линии + углы) → ректификация в 630×880
      → поиск строки коллекционера на ректифицированном кропе
      → OCR (Tesseract, несколько вариантов предобработки)
      → разбор строки (номера, код сета, язык, редкость)
      → агрегация по времени (сегменты показа) → отчёт JSON
```

### 1. Кандидаты-четырёхугольники (`src/detector.cpp`)

1. Кадр приводится к стороне не больше 1280 px, переводится в оттенки серого, размывается.
2. `cv::ximgproc::FastLineDetector` (Canny 25/80) даёт отрезки; короткие (<60 px) отбрасываются.
3. Отрезки склеиваются в прямые: близкие по углу (≤8°) и по расстоянию (≤12 px) объединяются.
4. Прямые делятся на «горизонтальные» и «вертикальные», из пар пар строятся четырёхугольники
   (пересечение прямых).
5. Проверки: площадь ≥1.2% кадра, стороны ≥10% меньшей стороны кадра, соотношение сторон
   0.35…1.05 (карта 63×88 мм = 0.716), выпуклость, углы ≥55°.
6. **Поддержка рёбрами**: доля каждого ребра квада, покрытая реальными отрезками
   (проекция + перпендикуляр ≤5 px). Требуется средняя поддержка ≥0.55 и ≥3 ребра с
   поддержкой ≥0.3, а также ≥2 угла рядом с концами отрезков (≤20 px).
   Это главный фильтр против «квадов из линий стола/рисунка».
7. **Уточнение границ** (`refineQuadOutward`): для каждого ребра ищутся локальные максимумы
   градиента в окне от −1% до +13% размера карты; выбирается самый внешний вариант с
   поддержкой ≥40% сэмплов. Нужен, чтобы попасть на внешнюю границу карты, а не на
   внутреннюю рамку.
8. NMS: подавляются только почти совпадающие квады (IoU >0.9, вложенность >0.98) —
   окончательный выбор делает анализ кропа.

### 2. Верификация кропа (`src/analyzer.cpp`, `src/evidence.cpp`)

Каждый кандидат ректифицируется в 630×880 (карта 63×88 мм при 10 px/мм).
Для кропа считаются признаки:

* `borderContrast`/`topBarContrast` — отличие внешней полосы от внутренней;
* `textRuns` — число глифов в полосе коллекционера (Otsu + связные компоненты);
* `SerialEvidence` — **сигнатура строки серийника**: полоса `y∈[0.88,0.995]`, `x∈[0.01,0.57]`,
  Otsu, тёмный фон + светлые глифы, ≥4 компоненты глифового размера.

Кандидат считается картой, если `serial.accepted` либо (контраст рамки ≥0.06 и runs ≥5).
Ранжирование: `geo_score × (1+2·structural) × (1+0.5·min(1,runs/8)) × serialBoost`,
где `serialBoost = 1+2·serial.score`, если сигнатура найдена, иначе 0.25.
Именно сигнатура серийника надёжно отличает карту от похожего по геометрии куска стола.

Кроп для OCR расширяется асимметрично: +1.5% по бокам и сверху, **+9% снизу** —
квад детектора часто оказывается чуть внутри нижней кромки, где и находится серийник.
Нижняя граница содержимого (`contentBottom`, доля высоты кропа) уточняется по изображению:
тёмная полоса рамки карты и первое просветление под ней — это либо стол, либо **тело карты,
лежащей под этой** (`contentBottomFromBorder`). Так строка коллекционера соседней карты
остаётся вне области поиска (см. §3, п.1).

### 3. Поиск строки коллекционера (`locateCollector`, `src/ocr.cpp`)

Фиксированные ROI не работают: положение нижней кромки «плавает» на несколько процентов.
Поэтому строки ищутся по изображению:

1. Область поиска: `x∈[0,52%]`, `y` от 72% до `contentBottom × (1+collector-margin)` кропа,
   апскейл ×3. Ниже `contentBottom` кроп держит полосу под квадом — это стол или **карта,
   лежащая позади**, и её строка коллекционера голосовала бы за чужую карту.
   Допуск `--collector-margin` (по умолчанию 5%) нужен потому, что детектор часто
   останавливается на внутренней кромке чёрной рамки, и своя строка оказывается чуть ниже квада.
2. CLAHE → морфологический **top-hat** (11×11) → нормализация → Otsu: выделяются мелкие
   светлые глифы независимо от фона.
3. Компоненты фильтруются по высоте (2–10% области) и ширине; группируются в строки
   по перекрытию по вертикали.
4. Берётся **самая нижняя** строка (это строка `SET · LANG artist`), блок = полоса
   `x` от 0.8% до 46% ширины кропа, `y` = ±2 высоты строки, обрезанная по `contentBottom`.
   Высота 1-й строки (`051/065 C`) попадает в этот блок с запасом.
5. Если строки не найдены — используются фиксированные ROI (fallback для нестандартных рамок).

Строка лежащей позади карты обычно не попадает в область поиска (п.1, `contentBottom`).
Когда она всё же читается (блистер с бликом, рамка нестандартной высоты), чтения разных
кодов сета перемежаются в сегменте показа — это ловит воздержание по перемежающимся
сетам (§6, п.4), а не по одному кадру: единственный кадр не доказывает, чья строка
прочитана.

### 4. OCR (`src/ocr.cpp`)

* Tesseract 5 (LSTM), язык `eng`; данные — `eng.traineddata` из системного `tessdata`.
* Предобработка: апскейл под высоту блока ≈260 px (фактор 2…10), лёгкий unsharp.
  Варианты: серое без порога (основной), адаптивный порог (THRESH_BINARY_INV, block 31, C 12),
  Otsu-инверсия.
* **Белая рамка вокруг ROI не добавляется**: Tesseract на белой рамке вокруг тёмной полосы
  возвращает пустой результат (проверено).
* Попытки: блок (psm 6), каждая найденная строка (psm 7), узкий кроп первых 6.5 высот строки
  с psm 8/7 для кода сета; адаптивные варианты блока.
* Строки нумеруются по регионам (0 — блок, 1 — строка номера, 2 — строка сета), и при
  слиянии голосов каждое поле берётся из «своего» региона: номер — из строки номера,
  код сета — из строки сета. Это устраняет типичную ошибку, когда блок читает `DDS` как `DOS`.

### 5. Разбор строки (`src/identity.cpp`, CTRE)

Регулярки — compile-time (библиотека **CTRE**, подключается через `FetchContent`,
пин `v3.9.0`). Текст нормализуется: верхний регистр, только ASCII, разделители `. , : ~ + - ;`
→ `*`.

* Номер: `(\d{1,4})\s*[/\\|I1L]\s*(\d{1,4})\s*([CURMSLTB])?` — допускает мисс-рид `/`
  как `1`, `I`, `L`, `|`, `\`.
* Перед разбором — исправление цифровых конфузий (`O,Q→0`, `I,L→1`, `S→5`, `B→8`, `Z→2`, `G→6`)
  только между цифрами.
* Санитизация: `total ≥ 20`, `1 ≤ number ≤ total`, иначе номер отбрасывается.
  Это отсекает, например, `4/4` из текста правил.
* Код сета + язык: `([A-Z][A-Z0-9]{1,5})[*\s]{1,4}(EN|RU|...)`; затем вариант с пробелом;
  затем fallback «код в начале строки» — `^\s*([A-Z][A-Z0-9]{2,4})[*\s]{1,3}[A-Z]{2,3}`.
* Языки: EN, RU, DE, FR, IT, ES, PT, JA, JP, KO, KR, ZH, ZHS, ZHT, CN, TW, SP, PL, NL, CS, SK,
  HU, TR, HE.
* При наличии словаря кодов сетов (`--set-codes` / `cardscan_set_set_codes`) код «прищёлкивается»
  к ближайшему известному по взвешенному расстоянию Левенштейна с картой конфузий
  (`O0DQ`, `I1LJT`, `S5`, `B8`, `Z2`, `G6C`, `A4`, `E3`, …); принимается только однозначный
  лучший вариант (d ≤ 1.05 и отрыв от второго > 0.2).
* `mergeReads` — голосование по всем попыткам; поле берётся из своего региона.

Словарь кодов сетов даёт бот: таблица `sets` (`auctions/topbot/schema.sql`) или Scryfall.
Движок сам ничего не скачивает.

### 6. Подсчёт карт в видео (`src/analyzer.cpp`)

Отслеживание квадов (IoU + смещение центра + ограничение по площади + **pHash-контроль**,
чтобы не склеить разные карты) используется для оверлея и для бюджета OCR.

Подсчёт не опирается на непрерывность трека (на быстрых перелистываниях треки рвутся):

1. Каждый `ocr_stride`-й кадр верхний кандидат (после верификации) читается целиком;
   результаты складываются в таймлайн `ReadSample{ts, identity, code, number, ...}`.
2. Таймлайн режется на **сегменты показа**: разрыв >`segmentGapSeconds` (0.6 c),
   либо смена кода сета — 3 чтения подряд (`segmentIncompatibleRun`) с
   `codeDistance` > `segmentCodeDistance` (2.5), либо длительность >`maxSegmentSeconds` (2.5 c),
   либо **тихая смена показа**: cleanly-прочитанный известный код сета (`--set-codes`)
   с `codeDistance` > `segmentShowDistance` (1.5) от мажоритарного кода сегмента, когда
   мажоритарный код молчит дольше `segmentGapSeconds` — показы разделены нечитаемыми
   кадрами, и счётчик несовместимости не успевает накопиться. Мажоритарный код должен
   иметь ≥2 чтений: одиночное чтение не доказывает показ, а мусорный код, случайно
   совпавший с известным сетом, иначе разрезает показ пополам.
3. Внутри сегмента номер выбирается посимвольным голосованием с выравниванием по длине
   (частая ошибка `051/065` ↔ `537/0637` иначе превращается в мусор), в два захода:
   сначала среди чтений, чей код сета согласуется с кодом сегмента (точный путь), а если
   там нет поддержки — среди всех чтений (карта, у которой код сета читается тремя
   разными способами, всё равно показывает один номер). Код сета затем уточняется по
   индексу печатей: берётся ближайший к прочитанным написаниям сет, в котором этот номер
   реально существует (`HashIndex::setWithNumber`).
4. Печатная строка называет карту только при двух условиях:
   * **парная поддержка** — пара «сет+номер» прочитана вместе ≥`minNumberSupport` (2) раз:
     номер, встретившийся один раз рядом со своим кодом, а в остальных чтениях без кода, —
     одна удачная рамка, не идентичность;
   * **перемежающиеся сеты** — если в сегменте два разных известных кода сета, каждый
     с ≥2 чтениями, и чтения одного из них лежат строго между чтениями другого,
     полоса видела **две строки коллекционера** (карта под показываемой): канал codes
     воздерживается,
     и идентичность решают картинка/название. Показ «The Ten Rings» поверх
     «Rampaging Baloths» так и остаётся `unknown` — чужая строка читается чище своей.
5. Сегмент с ≥`minSegmentReads` (5) чтениями считается картой; одинаковые `SET:number`
   склеиваются (`consolidateCards`) только если они соседние по времени
   (`duplicateMergeGapSeconds` 0.3 c) — повтор той же карты после паузы или другой карты
   это отдельная карта в стопке, а не тот же показ.
6. Идентичность также может дать картинка: pHash сужает круг кандидатов, ORB-проверка
   подтверждает (`docs/spec-scryfall-index.md`).

Все пороги подсчёта живут в `AnalyzerOptions` (`cards/src/analyzer.h`), пороги детектора —
в `DetectorParams`: в коде нет «магических чисел», поэтому под другой датасет их можно
подкрутить, не меняя логику. `bestCrop` освобождается, как только у трека появляется
надёжная идентичность (кроп нужен только для fallback по названию и для `--debug-dir`).

Карты, у которых номер не прочитан ни разу, остаются в отчёте как `identified=false`
(в счёт попадают, помечены `unknown`) — их количество и есть оценка «сколько ещё карт
не распознано».

### 6a. Детекция на выбранных кадрах (`--extract-cards`)

Детектор — самая дорогая часть (30-секундный ролик — минуты), поэтому прогон разделён:

1. `--extract-cards <video> <dir> [--frames a,b,c --frame-span n]` гонит детектор и
   верификацию только по нужным кадрам и сохраняет **по одному нормализованному
   прямоугольнику карты на показ** — кроп квада с полосой под ним (`content_bottom` в
   `manifest.tsv`). Показы склеиваются по времени (разрыв > `segmentGapSeconds`) и по
   общей картинке/месту квада, поэтому кадры одного показа дают один прямоугольник, а
   повторная карта после другой — новый (это же правило, что у дублей в §6, п.4).
   На показ хранится до 12 лучших кадров: распознавание голосует по ним.
2. `--cards <dir>` читает сохранённые прямоугольники и прогоняет то же голосование
   (`buildCardsFromReads`), без декодирования видео: секунды вместо минут.

Так работает `cards/tests/run_frame_check.sh`: 8 кадров (по одному на карту) — около
30 секунд на весь гейт.

## Ограничения и известные проблемы

* Мелкий текст (высота ~8–12 px в кадре 720p) читается Tesseract нестабильно: код сета —
  примерно в 35% чтений, номер — в 20%; улучшение требует большего разрешения или отдельной
  модели OCR.
* Оценка на `~/Documents/cards.mp4` (2026-11-22, индекс 19 423 печати): 13 карт, 7
  идентифицированы (`DDS:51`, `FIN:180`, `WAR:149`, `AKH:187`, `HOB:82`, `TMT:67`,
  `MSH:97`); остальные — `unknown`: карта в цветной обложке, нечитаемые показы и
  «The Ten Rings» (`MSH:251`), которая снята в блистере с бликом: своя строка
  коллекционера не читается, а строка лежащих под ней «Rampaging Baloths» (`C18:158`)
  читается, но перемежается чтениями `MSH` — срабатывает воздержание по перемежающимся
  сетам (§6, п.4), и карта остаётся `unknown` вместо чужой идентичности.
  Ложных идентичностей нет: лучше `unknown`, чем чужая карта.
* Кадры, где в кроп попадают две карты, обычно остаются `unknown`: соседняя строка не
  попадает в область поиска (`contentBottom`, §3, п.1), а если всё же читается —
  перемежающиеся сеты в сегменте заставляют канал codes воздержаться (§6, п.4).
* Быстрая проверка кадров (`cards/tests/run_frame_check.sh`) считает только несколько кадров
  на карту, поэтому распознаёт меньше карт, чем полный прогон: это гейт на *чужую* карту,
  полный счёт проверяется через `CARDSCAN_FULL=1 cards/tests/run_golden.sh`.
* Русские названия карт не читаются: в системе только `eng.traineddata`.
  Названия используются как fallback только для латиницы; `rus.traineddata` не скачивается.
* Асимметричное расширение кропа (+9% снизу) рассчитано на современные рамки MTG.
  Для старых белых рамок позиция строки коллекционера другая — сработает fallback «поиск строки».
* Цветовой дескриптор кропа не используется: замеры показали, что у одной и той же карты
  под разными углами расстояние больше, чем у разных карт. Идентичность по картинке даёт
  только keypoint-проверка (`docs/spec-scryfall-index.md`), склейка показов — по OCR и
  времени.
