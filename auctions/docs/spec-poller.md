# Спецификация поллера

Один поллер на всех пользователей. Никаких per-user циклов и никаких персональных запросов к TOPDeck.

## 1. Асинхронная схема

```
                 ┌──────────────────────────────────────────────┐
                 │                topbot (один процесс)         │
                 │                                              │
  Telegram  ◄────┤ aiogram 3.x  (long polling через прокси)     │
                 │        ▲                                     │
                 │        │ notify(user, event)                │
                 │   ┌────┴─────────────┐                       │
                 │   │  Notifier        │  dedupe + лимиты      │
                 │   └────▲─────────────┘                       │
                 │        │                                     │
  /healthz  ◄────┤ uvicorn (127.0.0.1:8080)                     │
                 │        │                                     │
                 │   ┌────┴──────────────────────────────┐      │
                 │   │ AuctionPoller (каждые 14 минут)   │      │
                 │   │  GET /apps/toptrade/auctions      │      │
                 │   │  → parse JSON → upsert lots       │      │
                 │   │  → match(lots × все watchlist)    │      │
                 │   │  → windows → Notifier             │      │
                 │   └────┬──────────────────────────────┘      │
                 │        │  состав лота (fetch_lot)            │
                 │   ┌────┴─────────────┐                       │
                 │   │ AdminAlerter     │  серии сбоев → админ  │
                 │   └──────────────────┘                       │
                 └──────────────────────────────────────────────┘
```

* `AuctionPoller` — `asyncio` task, интервал **840 с**, выровненный от старта процесса (`next_run = start + k*840`), без «догоняющих» пропусков.
* Пишет в БД и не общается с Telegram напрямую — только через `Notifier` (единая точка дедупликации, лимитов и тихих часов) и `AdminAlerter` (алерты о сбоях, см. §5).

## 2. Цикл опроса аукционов (каждые 14 минут)

1. `GET https://topdeck.ru/apps/toptrade/auctions` (gzip, ~54 КБ, ~1 c).
2. Разбор встроенного JSON → список лотов (порядка 350–400).
3. `upsert` в `lots`: `end_ts = date_estimated`, `first_seen = now`, `last_seen = now`, `state = active`.
4. Лоты, которых нет в ответе и у которых `end_ts < now` → `state = finished`.
5. Матчинг по названию: для каждого лота — список `card_id`, полученный из кэша `lot_cards`.
6. **Состав лота** (мультикарточные и «непонятные» лоты): пока у лота `composition_ts IS NULL` и он не сматчился по названию (или в названии есть маркеры сборника), поллер скачивает страницу лота и сохраняет состав в `lot_items` — бюджет **40 страниц за цикл**, приоритет по `end_ts` (что кончается раньше, то и разбираем первым). После появления состава матчинг пересчитывается (метод `composition:*`), поэтому мультилот с картой из watchlist попадает в уведомления.
7. Для каждой пары `(user, lot)`, где карта в watchlist'е пользователя:
   * `r = end_ts - now`;
   * набор включённых окон пользователя `W = {86400, 10800, 3600, 900}`;
   * окно `w` считается «попало», если `r <= w`, для `(user, lot, w)` нет **отправленной** записи, и `w` **уже́** любого уже отправленного окна (после «3 часа» «1 день» больше не приходит; после «1 день» «1 час» — приходит);
   * из попавших отправляем **только самое узкое** (если после простоя попали 1ч и 15м — отправляем 15м, чтобы не спамить).
8. Записываем `poll_runs(ts, lots, duration_ms, ok, error)`.

### Математика окон при шаге 14 минут

Поллер — это дискретизация с шагом 840 с, поэтому окно срабатывает в первый опрос, когда `r <= w`. Худший случай: лот «перепрыгнул» окно — уведомление придёт позже номинала (для окна 15 м — вплоть до ~1 минуты до конца).

Чтобы это было предсказуемо:

* порог срабатывания берём с запасом `w + 840/2` только для окон ≥ 1 ч (уведомление гарантированно не позже номинала и не раньше чем за `w + 7 мин`);
* для окна 15 минут порог = 900 с без запаса, и в тексте пишем **фактический** остаток («⏰ меньше 5 минут до конца», «⏰ 12 минут до конца»), а не название окна.

Пример таймлайна лота (окна 24ч/3ч/1ч/15м, шаг 14 мин):

```
t-24ч05м  опрос: r=24ч05м → тишина
t-23ч51м  опрос: r=23ч51м ≤ 24ч+7м → «до конца сутки»
t-3ч04м   опрос: r=3ч04м  → тишина
t-2ч50м   опрос: r=2ч50м  ≤ 3ч+7м → «до конца ~3 часа»
...
t-0ч12м   опрос: r=12м ≤ 15м → «меньше 15 минут» (факт: 12 минут)
```

## 3. Дедупликация и лимиты

* Ключ `notifications`: `(user_id, kind, ref_id, window)` — UNIQUE. Запись создаётся **до** отправки (at-most-once при падении — лучше пропустить, чем дважды спамить).
* **Отложенные уведомления не теряются**: если окно попало в тихие часы, запись получает `state='quiet_hours'` и не считается отправленной; на каждом следующем опросе поллер пробует снова (окно всё ещё `r <= w`) и отправит его, как только тихие часы закончатся — с фактическим остатком времени в тексте. Так же повторяются `rate_limited`/`failed`.
* Глобальный предохранитель: 20 сообщений/час на пользователя; лишние сворачиваются в одно «сводка».
* Тихие часы: 23:00–09:00 по TZ пользователя (по умолчанию `Europe/Moscow`). Переносятся окна 24ч/3ч/1ч; окно 15 минут — отправляется всегда.
* Пауза (`/mute`) глушит **все** окна, включая 15-минутное (в отличие от тихих часов): запись получает `state='muted'` и дошлётся, когда пауза кончится и окно ещё открыто.
* Повторная отправка при `TelegramRetryAfter` — не считается новым событием (id события сохраняется).

## 4. Отказоустойчивость

* HTTP: таймаут 30 с, 3 попытки с backoff 2/5/15 с, `User-Agent: topbot/<version> (+contact)`, gzip обязателен.
* 3 подряд неудачных опроса → уведомление админу + `state=degraded` в `/healthz`; после восстановления — сообщение «опрос восстановился». Два опроса подряд с `0` лотов → отдельный алерт («сайт изменил вёрстку или недоступен»). Повторный алерт того же типа — не чаще раза в час; получатели — `ADMIN_TG_IDS` плюс найденные по `ADMIN_USERNAMES` (`users.username`, id резолвится через БД, неизвестный ник — warning в лог).
* Пропущенные окна во время простоя: после восстановления отправляем только те окна, чей порог ещё не истёк; истёкшие — помечаем `skipped` (без «догоняющих» пачек).
* Смена заголовка лота/времени окончания: `lot_cards` инвалидируется при изменении `lot`, `end_ts` обновляется всегда (важно, если продление аукциона существует — см. research §11.1).
* Схема БД мигрируется через `alembic`-совместимые версии (`schema_version` в `meta`).

## 5. Наблюдаемость

* `poll_runs` (ts, kind, duration_ms, ok, error, items) — история опросов для `/status` и `/admin`.
* `/healthz`: `{status, lots_active, last_auction_poll_age_s}`.
* Логи: `INFO` — цикл и счётчики, `WARNING` — retry/degraded, `ERROR` — исключения с трейсом.

### 5.1 Логи (структурные)

`topbot/logs.py`: единая настройка через `.env` (`LOG_LEVEL`, `LOG_FORMAT=text|json`, `LOG_FILE`). В stdout — текст с полями `key=value`, в файл — **всегда JSON Lines** с ротацией (10 МБ × 5). `aiogram.event` приглушён до `WARNING`, чтобы не забивать лог «Update is handled».

Что пишется (каждая запись — с полями, готовыми к `jq`/grep):

| Событие | Поля |
|---|---|
| `topdeck fetch` | `path, status, chars, ms` |
| `topdeck auctions parsed` / `topdeck singles search` | `lots` / `cards, offers, truncated, sources` |
| `scryfall request` | `path, status, ms, attempt` (+ `scryfall rate limited` с `retry_after`) |
| `auction poll received` / `auction poll done` | `lots` / `lots, matched_lots, watched_lots, notifications, vanished, ms` |
| `lot matches watchlist` | `lot_id, cards, watched, ends_in_min` |
| `notify decision` / `notification delivered` | `user_id, kind, ref_id, window_s, decision` / `notification_id` |
| `add request` / `resolve query` | `user_id, raw` / `query, candidates, top` |
| `pick candidate` / `card added` | `user_id, index, name` / `card, new` |
| `price request` | `user_id, query, offers, truncated` |
| `update received` / `update handled` | `kind (Message/CallbackQuery), user_id, payload (до 80 симв.), ms` |
| `handler failed` | `update_id` + трейс |

Пример текстового лога:

```
2026-11-16 00:12:31 INFO  topbot.poller auction poll done | lots=365 matched_lots=3 watched_lots=1 notifications=1 vanished=2 ms=843
2026-11-16 00:12:31 INFO  topbot.notifier notification delivered | notification_id=57 user_id=100000001 kind=auction_window ref_id=550068
```

Ротация и JSON-файл позволяют разбирать инциденты постфактум (`jq 'select(.level=="ERROR")' data/logs/bot.jsonl`).
