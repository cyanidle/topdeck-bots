# Спецификация поллера

Один поллер на всех пользователей. Никаких per-user циклов и никаких персональных запросов к TOPDeck.

## 1. Асинхронная схема

```
                 ┌──────────────────────────────────────────────┐
                 │                topbot (один процесс)         │
                 │                                              │
  Telegram  ◄────┤ aiogram 3.x  (long polling через прокси)     │
                 │        ▲                                     │
                 │        │ notify(user, event)                │
                 │   ┌────┴─────────────┐                       │
                 │   │  Notifier        │  dedupe + лимиты      │
                 │   └────▲─────────────┘                       │
                 │        │                                     │
  /healthz  ◄────┤ uvicorn (127.0.0.1:8080)                     │
                 │        │                                     │
                 │   ┌────┴──────────────────────────────┐      │
                 │   │ AuctionPoller (каждые 14 минут)   │      │
                 │   │  GET /apps/toptrade/auctions      │      │
                 │   │  → parse JSON → upsert lots       │      │
                 │   │  → match(lots × все watchlist)    │      │
                 │   │  → windows → Notifier             │      │
                 │   └────┬──────────────────────────────┘      │
                 │        │  состав лота (fetch_lot)            │
                 │   ┌────┴─────────────┐                       │
                 │   │ AdminAlerter     │  серии сбоев → админ  │
                 │   └──────────────────┘                       │
                 └──────────────────────────────────────────────┘
```

* `AuctionPoller` — `asyncio` task, интервал **840 с**, выровненный от старта процесса (`next_run = start + k*840`), без «догоняющих» пропусков.
* `PricePoller` — отдельный `asyncio` task, интервал **900 с** (`PRICES_INTERVAL_S`): один прогон = один-два запроса `singles/search` на пачку из 8 карт по объединению карт из всех watchlist'ов, результат кладётся в `card_offers`/`card_price_sync`. Бот (`/list`, `/price`) читает только кэш.
* `WindowScheduler` — `asyncio` task, который шлёт окна уведомлений (см. §2, «Точность окон»). Пишет в БД и общается с Telegram только через `Notifier` (дедупликация, лимиты, пауза `/mute`); алерты о сбоях поллера — `AdminAlerter` (см. §5).

## 2. Цикл опроса аукционов (каждые 14 минут)

1. `GET https://topdeck.ru/apps/toptrade/auctions` (gzip, ~54 КБ, ~1 c).
2. Разбор встроенного JSON → список лотов (порядка 350–400).
3. `upsert` в `lots`: `end_ts = date_estimated`, `first_seen = now`, `last_seen = now`, `state = active`.
4. Лоты, которых нет в ответе и у которых `end_ts < now` → `state = finished`.
5. Матчинг по названию: для каждого лота — список `card_id`, полученный из кэша `lot_cards`.
6. **Состав лота** (мультикарточные и «непонятные» лоты): пока у лота `composition_ts IS NULL` и он не сматчился по названию (или в названии есть маркеры сборника), поллер скачивает страницу лота и сохраняет состав в `lot_items` — бюджет **40 страниц за цикл**, приоритет по `end_ts` (что кончается раньше, то и разбираем первым). После появления состава матчинг пересчитывается (метод `composition:*`), поэтому мультилот с картой из watchlist попадает в уведомления.
7. Записываем `poll_runs(ts, lots, duration_ms, ok, error)`. Уведомления поллер не отправляет — это делает `WindowScheduler` (см. ниже).

### Точность окон: отдельный планировщик, а не шаг поллера

Поллер (840 с) только собирает лоты и считает матчи — уведомления он не шлёт. За окна отвечает `WindowScheduler` (`topbot/scheduler.py`):

* каждые ≤ 60 с (`TICK_S`) он пересчитывает план по БД (`Database.planned_windows` → `fire_at = end_ts - window` для каждой пары «карта из watchlist × включённое окно») и спит ровно до ближайшего `fire_at`, если тот ближе тика;
* сами правила выбора окна прежние (`windows.due_window`): окно годится, если `remaining <= w`, оно ещё не отправлено и `w` **уже́** любого отправленного; из подходящих берётся **самое узкое** (после простоя попали «1 ч» и «15 м» — уходит только «15 м»);
* в момент `end_ts - w` вызывается та же рассылка, что раньше жила в поллере (`dispatch.dispatch_lot_windows`), поэтому окно уходит **минута в минуту**: срабатывание в пределах ±1 с от номинала (целые секунды в `delay`), никогда не раньше;
* текст окна собирает `messages.render_auction_message`; цены продавцов (`💰 Цены у продавцов: …`, до 3 самых дешёвых, по одному — самому дешёвому — на продавца) берутся **из кэша** `card_offers` (`Database.top_offers_by_card`, лимит `messages.INLINE_OFFERS`), живых запросов к `singles/search` при рассылке нет — иначе рассылка зависела бы от сети и от скорости TopDeck; запрос ленивый: только когда окно реально назрело;
* запаса `w + 420 с` больше нет: досрочных отправок не бывает, `due_window` требует `remaining <= w`; опоздание возможно только после простоя и ограничено правилом `remaining >= w // 2` (иначе окно считается истёкшим);
* дедупликация та же (`notifications`, `state='sent'`), поэтому перезапуск процесса не приводит к повторной отправке: план строится по фактическим записям в БД;
* отложенные окна (`/mute`, лимит) остаются в плане и переотправляются на следующем тике — теперь раз в минуту, а не раз в 14 минут.

Пример таймлайна лота (окна 24ч/3ч/1ч/15м):

```
t-24ч00м00с  планировщик: r=24ч00м → «до конца сутки»
t-3ч00м00с   планировщик: r=3ч00м  → «до конца ~3 часа»
t-1ч00м00с   планировщик: r=1ч00м  → «до конца ~1 час»
t-0ч15м00с   планировщик: r=15м00с → «до конца ~15 минут»
```

В тексте — **фактический** остаток (`humanize_remaining(remaining)`), а не название окна.

## 2.1 Цикл обновления цен (каждые 15 минут)

1. Берём объединение карт из всех watchlist'ов: `SELECT DISTINCT c.* FROM cards c JOIN watchlist w` (`Database.watched_cards`).
2. Режем на пачки по 8 карт и на каждую делаем `GET /apps/toptrade/singles/search?q=<имена через \n>` (троттлинг клиента 1.5 с между запросами).
3. Ответ матчим к картам по `normalize(name)` — это поле содержит карту из строки продавца, а `eng_name`/`rus_name` в ответе TOPDeck — лишь канонизированный запрос (`prices.match_cards`); офферы с `cost <= 0`, без `name` и с ценой, равной номеру коллекционера из `line` (`#19`, `№271` — TOPDeck иногда парсит номер как цену), отбрасываем. Без этого нечёткий ответ («Shallow Grave» → «Curse of Shallow Graves») приклеивает чужие карты к нашей.
4. На карту — `save_card_offers`: дедуп по продавцу (остаётся самый дешёвый), строки в `card_offers`, отметка «опрошено» в `card_price_sync` (в т.ч. когда предложений нет — иначе карта будет считаться несобранной).
5. Кэш чистится от карт, которых больше нет ни в одном watchlist'е (`prune_card_offers`).
6. `poll_runs(kind='prices', items=число карт, duration_ms, ok)`.

Первый прогон — сразу на старте процесса, дальше — раз в 900 с. Падение прогона только логируется и пишется в `poll_runs` (админа не будим: цены — не критичный путь). Если усечённый ответ упирается в потолок записей, пачка делится пополам и запрашивается заново.

Ленивый запрос из бота: если карта попала в `/list`/`/price`, но в `card_price_sync` её нет (только что добавлена), бот сам забирает цены по ней — пачками по 8 карт (у пользователя с 20 новыми картами это 3 запроса). Дальше — только кэш: `/list` отвечает за ~3 мс вместо ~6–7 с.

## 3. Дедупликация и лимиты

* Ключ `notifications`: `(user_id, kind, ref_id, window)` — UNIQUE. Запись создаётся **до** отправки (at-most-once при падении — лучше пропустить, чем дважды спамить).
* **Отложенные уведомления не теряются**: если у пользователя пауза (`/mute`) или исчерпан часовой лимит, запись получает `state='muted'`/`'rate_limited'` и не считается отправленной; `WindowScheduler` пробует снова на каждом тике (окно всё ещё `r <= w`) и отправит его, как только пауза кончится или освободится лимит — с фактическим остатком времени в тексте. Так же повторяются `failed`.
* Глобальный предохранитель: 20 сообщений/час на пользователя; лишние сворачиваются в одно «сводка».
* Время суток бот не учитывает: тихих часов нет — ночная тишина настраивается в клиенте Telegram («Не беспокоить») или паузой `/mute`.
* Пауза (`/mute 1h|8h|off`) глушит **все** окна, включая 15-минутное: запись получает `state='muted'` и дошлётся, когда пауза кончится и окно ещё открыто.
* Повторная отправка при `TelegramRetryAfter` — не считается новым событием (id события сохраняется).

## 4. Отказоустойчивость

* HTTP: таймаут 30 с, 3 попытки с backoff 2/5/15 с, `User-Agent: topbot/<version> (+contact)`, gzip обязателен.
* 3 подряд неудачных опроса → уведомление админу + `state=degraded` в `/healthz`; после восстановления — сообщение «опрос восстановился». Два опроса подряд с `0` лотов → отдельный алерт («сайт изменил вёрстку или недоступен»). Повторный алерт того же типа — не чаще раза в час; получатели — `ADMIN_TG_IDS` плюс найденные по `ADMIN_USERNAMES` (`users.username`, id резолвится через БД, неизвестный ник — warning в лог).
* Пропущенные окна во время простоя: после восстановления отправляем только те окна, чей порог ещё не истёк; истёкшие — помечаем `skipped` (без «догоняющих» пачек).
* Смена заголовка лота/времени окончания: `lot_cards` инвалидируется при изменении `lot`, `end_ts` обновляется всегда (важно, если продление аукциона существует — см. research §11.1).
* Схема БД мигрируется через `alembic`-совместимые версии (`schema_version` в `meta`).

## 5. Наблюдаемость

* `poll_runs` (ts, kind, duration_ms, ok, error, items) — история опросов для `/status` и `/admin`.
* `/healthz`: `{status, lots_active, last_auction_poll_age_s}`.
* Логи: `INFO` — цикл и счётчики, `WARNING` — retry/degraded, `ERROR` — исключения с трейсом.

### 5.1 Логи (структурные)

`topbot/logs.py`: единая настройка через `.env` (`LOG_LEVEL`, `LOG_FORMAT=text|json`, `LOG_FILE`). В stdout — текст с полями `key=value`, в файл — **всегда JSON Lines** с ротацией (10 МБ × 5). `aiogram.event` приглушён до `WARNING`, чтобы не забивать лог «Update is handled».

Что пишется (каждая запись — с полями, готовыми к `jq`/grep):

| Событие | Поля |
|---|---|
| `topdeck fetch` | `path, status, chars, ms` |
| `topdeck auctions parsed` / `topdeck singles search` | `lots` / `cards, offers, truncated, sources` |
| `scryfall request` | `path, status, ms, attempt` (+ `scryfall rate limited` с `retry_after`) |
| `auction poll received` / `auction poll done` | `lots` / `lots, matched_lots, watched_lots, vanished, compositions, ms` |
| `lot matches watchlist` | `lot_id, cards, watched, ends_in_min` |
| `window scheduler started` / `windows dispatched` | `tick_s` / `sent` |
| `notify decision` / `notification delivered` | `user_id, kind, ref_id, window_s, decision` / `notification_id` |
| `add request` / `resolve query` | `user_id, raw` / `query, candidates, top` |
| `pick candidate` / `card added` | `user_id, index, name` / `card, new` |
| `price request` | `user_id, query, offers, truncated` |
| `update received` / `update handled` | `kind (Message/CallbackQuery), user_id, payload (до 80 симв.), ms` |
| `handler failed` | `update_id` + трейс |

Пример текстового лога:

```
2026-11-16 00:12:31 INFO  topbot.poller auction poll done | lots=365 matched_lots=3 watched_lots=1 vanished=2 compositions=0 ms=843
2026-11-16 00:12:31 INFO  topbot.dispatch auction notification | user_id=100000001 lot_id=550068 window_s=900 remaining_s=900 delivered=True
2026-11-16 00:12:31 INFO  topbot.notifier notification delivered | notification_id=57 user_id=100000001 kind=auction_window ref_id=550068
```

Ротация и JSON-файл позволяют разбирать инциденты постфактум (`jq 'select(.level=="ERROR")' data/logs/bot.jsonl`).
